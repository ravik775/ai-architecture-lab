````md
# Loan Processing Architecture

This project is a Spring Boot microservices-based loan processing system with service discovery, resilience patterns, Redis/RabbitMQ infrastructure, and SPIFFE/SPIRE-based workload identity for secure service-to-service communication.

---

## 1. High-Level Overview

The system contains:

- **API Gateway**: Entry point for client traffic. Built with Spring Cloud Gateway WebFlux. Handles routing, retry, rate limiting, and circuit breaker behavior.
- **Loan Service**: Core business service exposing loan APIs.
- **Service Registry**: Eureka server used for dynamic service discovery.
- **Redis**: Used by gateway rate-limiting logic.
- **RabbitMQ**: Used for asynchronous messaging.
- **SPIRE Server + SPIRE Agent**: Issues workload identities as short-lived X.509-SVID certificates.
- **SPIFFE Helper Sidecars**: Fetch SVID certificates from SPIRE Agent and write them to shared volumes.

---

## 2. Runtime Architecture

Client calls:

```text
Client
  |
  v
API Gateway :8085
  |
  | Eureka lookup: LOAN-SERVICE
  | mTLS using Gateway SVID
  v
Loan Service : random or fixed HTTPS port
````

SPIRE identity flow:

```text
SPIRE Server
  |
  | registration entries
  v
SPIRE Agent
  |
  | Workload API socket
  v
spiffe-helper sidecar
  |
  | writes SVID files
  v
/spiffe-certs/svid.pem
/spiffe-certs/svid_key.pem
/spiffe-certs/bundle.pem
```

## 3. Security Model

This system uses SPIFFE/SPIRE instead of static service passwords.

### Key Concepts

* **SPIFFE ID**: Stable workload identity, for example:

    * `spiffe://example.org/ns/loan/sa/loan-service`
    * `spiffe://example.org/ns/loan/sa/api-gateway`

* **SVID**: Short-lived X.509 certificate issued by SPIRE.

* **Workload Attestation**: SPIRE Agent verifies the workload before issuing an SVID.

* **mTLS**: Both gateway and loan service prove their identity using certificates.

* **Trust Bundle**: `bundle.pem` is used to verify certificates issued by SPIRE.

## 4. Workload Attestation

The project uses the SPIRE **Unix Workload Attestor**.

Each helper container runs under a dedicated UID:

| Workload     | Helper UID | SPIFFE ID                                      |
| ------------ | ---------: | ---------------------------------------------- |
| Loan Service |    `10001` | `spiffe://example.org/ns/loan/sa/loan-service` |
| API Gateway  |    `10002` | `spiffe://example.org/ns/loan/sa/api-gateway`  |

SPIRE bootstrap registers entries like:

```bash
-selector "unix:uid:10001" -dns "loan-service"
-selector "unix:uid:10002" -dns "api-gateway"
```

The DNS SAN is important because Java HTTPS hostname validation expects names like:

```text
https://loan-service:<port>
```

## 5. Shared `.env.sb`

`.env.sb` can be shared by gateway and loan service only if it contains common infrastructure values.

Recommended:

```env
REDIS_HOST=redis
REDIS_PORT=6379
REDIS_PASSWORD=change-this-redis-password

RABBITMQ_HOST=rabbitmq
RABBITMQ_PORT=5672
RABBITMQ_USERNAME=admin
RABBITMQ_PASSWORD=change-this-rabbit-password

RABBITMQ_DEFAULT_USER=admin
RABBITMQ_DEFAULT_PASS=change-this-rabbit-password

EUREKA_CLIENT_SERVICEURL_DEFAULTZONE=http://service-registry:8086/eureka/
EUREKA_INSTANCE_PREFER_IP_ADDRESS=false

SPIFFE_ENDPOINT_SOCKET=unix:///tmp/spire-agent/public/api.sock
```

Do not keep these in shared `.env.sb`:

```env
SERVER_SSL_KEY_STORE=...
SERVER_SSL_TRUST_STORE=...
KEYSTORE_PASSWORD=...
TRUSTSTORE_PASSWORD=...
JOIN_TOKEN=...
```

SPIRE join token is generated by `spire-bootstrap` and shared through a Docker volume.

## 7. Validate SPIRE

Show SPIRE registration entries:

```powershell
docker compose exec spire-server /opt/spire/bin/spire-server entry show -socketPath /tmp/spire-server/private/api.sock
```

Expected selectors:

```text
Selector : unix:uid:10001
Selector : unix:uid:10002
```

Check loan SVID files:

```powershell
docker compose exec loan-service-spiffe-helper ls -l /spiffe-certs
```

Check gateway SVID files:

```powershell
docker compose exec api-gateway-spiffe-helper ls -l /spiffe-certs
```

Expected:

```text
bundle.pem
svid.pem
svid_key.pem
```

Inspect loan certificate SAN:

```powershell
docker run --rm -v loan-processing-architecture_spiffe-loan-certs:/certs alpine:3.20 sh -c "apk add --no-cache openssl >/dev/null && openssl x509 -in /certs/svid.pem -noout -ext subjectAltName"
```

Expected:

```text
URI:spiffe://example.org/ns/loan/sa/loan-service
DNS:loan-service
```

Inspect gateway certificate SAN:

```powershell
docker run --rm -v loan-processing-architecture_spiffe-gateway-certs:/certs alpine:3.20 sh -c "apk add --no-cache openssl >/dev/null && openssl x509 -in /certs/svid.pem -noout -ext subjectAltName"
```

Expected:


## 9. Validate Gateway Routing

Call gateway:

```powershell
curl.exe http://localhost:8085/loan?from=Gateway
```

With tenant header:

```powershell
curl.exe -H "X-Tenant-Id: tenant-a" http://localhost:8085/loan?from=Gateway
```

Check gateway logs:

```powershell
docker compose logs --tail=100 api-gateway
```

Filter forwarding logs:

```powershell
docker compose logs api-gateway | Select-String "resolvedTargetUri"
```

Expected:

```text
resolvedTargetUri=https://loan-service:<port>/loan?from=Gateway
Gateway response: targetUri=https://loan-service:<port>/loan?from=Gateway, status=200 OK
```

This proves gateway resolved `LOAN-SERVICE` through Eureka and routed using HTTPS.

## 10. Validate mTLS Enforcement

Negative test: direct call without client certificate should fail.

If loan service is exposed locally:

```powershell
curl.exe -k https://localhost:8080/loan?from=Direct
```

Expected: TLS/client certificate failure.

Positive test with gateway SVID:

```powershell
docker run --rm --network loan -v loan-processing-architecture_spiffe-gateway-certs:/certs alpine:3.20 sh -c "apk add --no-cache curl >/dev/null && curl --cert /certs/svid.pem --key /certs/svid_key.pem --cacert /certs/bundle.pem https://loan-service:8080/loan?from=GatewaySVID"
```

Expected:

```text
This is from Loan SErvice: From GatewaySVID
```

## 11. Random Port For Loan Service

Loan service can run on a random port:

```yaml
server:
  port: ${SERVER_PORT:0}
```

Do not hardcode:

```yaml
eureka.instance.secure-port: 8080
```

Validate Eureka publishes the actual port:

```powershell
curl.exe http://localhost:8086/eureka/apps/LOAN-SERVICE
```

Expected:

```xml
<securePort enabled="true">random-port</securePort>
```

Gateway logs should show:

```text
resolvedTargetUri=https://loan-service:<random-port>/loan
```

## 13. Common Issues And Fixes

| Issue                                        | Cause                                          | Fix                                                             |
| -------------------------------------------- | ---------------------------------------------- | --------------------------------------------------------------- |
| `spiffe-helper` says `no identity issued`    | SPIRE selector mismatch                        | Check `entry show` and helper UID                               |
| `/spiffe-certs` empty                        | Helper did not receive SVID                    | Check helper and agent logs                                     |
| `api.sock no such file`                      | SPIRE agent did not start                      | Check `spire-bootstrap` and `spire-agent`                       |
| Gateway tries `loan-service-keystore.p12`    | Old `SERVER_SSL_*` vars leaking from `.env.sb` | Remove old keystore vars                                        |
| Gateway resolves `http://loan-service`       | Eureka not advertising secure port             | Set `secure-port-enabled=true`, `non-secure-port-enabled=false` |
| Eureka `/eureka/` returns 404                | Wrong URL for dashboard                        | Use `/eureka/apps` API or `/` dashboard                         |
| Loan registers port `0`                      | Random port not propagated                     | Check Eureka securePort and server port config                  |
| Direct loan HTTPS call succeeds without cert | mTLS not enforced                              | Ensure `server.ssl.client-auth=need`                            |

## 14. Review Closure Statement

Use this when explaining the design:

> This system runs a real SPIRE server and agent in Docker Compose. Workloads are attested through Unix selectors using isolated helper UIDs. SPIRE issues X.509-SVIDs for `api-gateway` and `loan-service`. The gateway presents its SVID when calling loan service, and loan service requires client certificates. Eureka advertises loan service as a secure instance, so gateway resolves it to an HTTPS endpoint. Internal headers become trustworthy only after they are carried over this SVID-authenticated mTLS channel.
